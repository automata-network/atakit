# Portal External API Specification

The portal exposes two external HTTPS surfaces, both served by the worker process. Both use a shared self-signed ECDSA P-256 certificate generated by the supervisor at first boot and passed to the worker at fork time.

The worker sends privileged requests through `SupervisorClient`. One background
task owns its connection and completes each request and reply before starting
the next request. The queue holds at most one waiting request. It skips a queued
request whose caller was cancelled. Once transmission starts, it finishes the
exchange even if the caller is cancelled, so a later caller cannot receive the
earlier reply. Cancellation therefore does not undo an operation already sent.
Any exchange error closes the connection and fails waiting calls. The client
does not reconnect or automatically replay requests.

## Ports

| Port | Lifetime | Purpose |
|---|---|---|
| 1024 | Transient. Firewall opens at boot (AwaitingInit). Closes when the firewall transitions to the workload ruleset (during InitializingWorkload). Never reopened. | `POST /init` only. |
| 2024 | Persistent. Always in firewall allow-list. | Status, measurement, TLS attestation, current-session, evidence, and owner lifecycle APIs. |

Both ports are maintained by the portal's always-allowed set, independent of the workload manifest's `[config.firewall-ports]`. Workload manifest-declared ports open in addition, during InitializingWorkload (after integrity verification and disk mounting). Both ports are bound by the worker; the supervisor never handles HTTP traffic.

## Firewall rules by state

| State | `:1024` | `:2024` | Workload manifest ports |
|---|---|---|---|
| AwaitingInit | open | open | not applied yet |
| Initializing | open | open | not applied (workload ports unknown until manifest is parsed) |
| InitializingWorkload (before firewall) | open* | open | not applied (verifying integrity, mounting disks) |
| InitializingWorkload (after firewall, optional/off) | closed | open | open (containers starting) |
| InitializingWorkload (after firewall, required) | closed | open | closed while containers start |
| Registering | closed | open | closed while containers run and registration remains unconfirmed |
| Running | closed | open | open |
| CleanHalt | n/a (rebooting) | n/a | n/a |
| Failed | closed | open | closed |

\* First init only. On reboot from Running/CleanHalt, :1024 is never opened — the supervisor skips it since /init cannot be accepted.

The InitializingWorkload firewall update always closes `:1024`. Under optional/off registration it also opens workload manifest ports; under required registration it keeps those ports closed while containers start and the portal enters `Registering`. After `isSessionActive(session_id)` succeeds, the verifier applies the full ruleset and transitions to `Running`.

`registration = "required"` gates the workload manifest-declared inbound ports.
It does not gate workload process execution. The workload containers start
before registration confirmation because the session uses a post-launch TPM
Quote. While the portal remains in `Registering`, those processes may perform
any action allowed by their container configuration, including outbound
connections, filesystem writes, and background work. The portal firewall does
not claim to prevent those effects.

For this transition, `isSessionActive(session_id)` succeeds when the configured
`chain.rpc_url` returns `true`. The portal does not verify a consensus proof,
block-header chain, state proof, or agreement among independent RPC endpoints.
An actor that controls `chain.rpc_url` can therefore cause a false transition
from `Registering` to `Running`.

Each firewall update is sent by the worker through `ApplyFirewall` RPC; the supervisor replaces only `table inet portal` via `nft -f`, leaving non-portal nftables tables such as netavark/Podman networking rules intact. If the portal crashes in `Initializing`, a subsequent restart rolls back to `AwaitingInit`. If it crashes in `InitializingWorkload`, it transitions to `Failed` (`:1024` remains closed, operator must redeploy).

## Endpoints

The v0.3.7 persistent listener also serves verified manifest retrieval and
owner-authorized full unmeasured-data replacement. See the
[unmeasured-data update specification](unmeasured-data-update-spec.md) for routes,
signed upload fields, privacy rules, limits and next-boot activation. These
updates reuse deployment validation and staging. They do not use `/init` transfer
IDs and do not provision another VM.

### `POST /init` (`:1024`, AwaitingInit only, one-shot)

Received by the worker, which drives the init flow and delegates privileged operations to the supervisor via RPC. The endpoint requires a signed initialization intent when a public bootstrap was provisioned. Without a bootstrap, it accepts unsigned initialization. The supervisor checks launch metadata before opening the listener; lookup failures or invalid bootstrap data stop startup. See [authenticated initialization](init-auth-spec.md) for bootstrap delivery, `GET /init/challenge` on the status port, the `Atakit-Init-Authorization` header, and failure behavior. Operators must still verify the portal's attested TLS certificate before sending secrets.

**Request**: `multipart/form-data`

New clients send `Atakit-Transfer-Id: <uuid-v4>`. The portal echoes this
correlation value in `/status` and the final success or error response. The
portal generates a UUID v4 when an older client omits the header. The value is
not an authentication credential.

New clients also send
`Atakit-Atawl-Transfer-Timeout-Seconds: <positive-integer>`. One value controls
only the ATAWL transfer. It covers receipt of a binary `atawl` part or the
portal's download of a remote ATAWL. Older clients may omit the header; the
portal then uses 300 seconds. The timeout does not cover extraction,
measurement, proving, registration, or waiting for `Running`.

Current clients send `Atakit-Init-Timeout-Seconds: <positive-integer>`. The
portal enforces this as one non-transfer budget from the start of `/init`. The
budget pauses only while the portal receives or downloads the ATAWL. Config and
unmeasured-data receipt before a remote download consume this budget, as do all
later `/init` phases. The success response reports the measured transfer
duration so the client can continue the same deadline while it waits for
`Running`. An older client may omit this header; the portal then preserves the
older client-managed initialization behavior. If the deadline expires after
prover or workload resources exist, the portal signals cancellation and waits
for the active phase to reach a safe boundary. It then wipes the workload PCR
binding, stops the prover and containers, locks workload data disks, and only
then records terminal `Failed`.

There is no fixed size cap for the ATAWL archive or unmeasured-data archive.
The operator provides and pays for that storage, so disk capacity is the limit.
Uploads and copies stream to disk. The small JSON parts have explicit limits,
including the 16 KiB remote descriptor limit below. If storage fills, `/init`
fails cleanly and does not publish partial data or service views. This
assumption is safe only while network policy prevents other actors from
reaching the unauthenticated endpoint.

| Part | Type | Required | Description |
|---|---|---|---|
| `atawl` | binary or JSON | yes | `application/octet-stream` carries the `.atawl` archive. `application/vnd.atakit.atawl-source+json` carries a remote-source descriptor. Exactly one part is accepted. See [atawl-archive-spec.md](atawl-archive-spec.md). |
| `config` | JSON | yes | Init-time configuration (see below). |
| `unmeasured-data` | binary | no | Operator-provided tar.gz (gzip-compressed tar) of unmeasured files. The portal stages this upload outside the measured `.atawl` extraction directory, so an archive entry cannot replace the operator upload before validation. The manifest's top-level `unmeasured-data` array is an attested exact-path allowlist committed to PCR23. The extracted file set must be a subset: undeclared uploaded paths fail `/init` with `unmeasured_data_mismatch`, while absent declared paths are allowed. If this part is omitted, the portal publishes an empty unmeasured-data tree. The extractor accepts regular files and directories only and rejects links, special files, traversal, and duplicate paths. File contents, presence, and validity are not verified by the portal. |

Binary upload clients may add `Atakit-Archive-Size` and
`Atakit-Archive-Sha256` to the `atawl` part. The portal uses the size for
progress and rejects a size or complete-file SHA-256 mismatch. Uploads without
these part headers remain valid and report an unknown total.

Remote-source descriptor format 1 is strict JSON with a 16 KiB limit:

```json
{
  "format": 1,
  "uri": "https://artifacts.example.com/workload.atawl",
  "archive_sha256": "0x...",
  "archive_size_bytes": 1073741824,
  "workload_id": "0x..."
}
```

`archive_sha256` hashes the complete `.atawl` file, not `manifest.json`.
`archive_size_bytes` is required and non-zero. After extraction, the portal
derives the workload ID from the measured manifest and compares it with
`workload_id`.

Clients must check the exact serialized JSON byte length before `POST /init`.
A descriptor of exactly 16 KiB is valid. A larger descriptor is a client
configuration error and must not consume the one-shot request.

The remote downloader accepts HTTP and HTTPS, including private repository
addresses. It blocks loopback, link-local, multicast, unspecified, cloud
metadata, NAT64 encodings of blocked IPv4 destinations, and other
special-purpose destinations. The portal rejects the complete
`64:ff9b:1::/48` local-use translation range because that reservation permits
several translation layouts and the portal has no operator-specific prefix
configuration with which to decode it safely. It validates every DNS
result and redirect, allows at most five redirects, and rejects HTTPS-to-HTTP
redirects. HTTP provides no confidentiality; the exact size and SHA-256 still
protect archive integrity. HTTPS always uses normal certificate validation.
The portal applies one absolute ATAWL transfer deadline across name
resolution, every redirect, connection setup, and all response-body reads.
Progress does not reset that deadline. The same absolute deadline applies
while the portal receives a binary ATAWL upload. On timeout, the portal removes
the partial archive, enters terminal `Failed`, and returns
`atawl_transfer_timeout` with HTTP 504.

The URI is held only for the active download. `/status`, error bodies,
supervisor state, and logs never contain the URI, a redacted URI, a URI hash,
or redirect targets.

The portal extracts unmeasured data into a temporary canonical tree. After validation, the supervisor freezes that tree as root-owned read-only data. It creates one atomic private view per service using reflinks when available and independent copies otherwise. Each container receives one view mount at `/atakit-portal/unmeasured-data/` with `readonly`, `noexec`, `nosuid`, and `nodev`. The canonical tree is never container-visible.

Unmeasured env files use the same upload. Format 5 measures the allowed variable names for each env-file path. A declared runtime env file may be absent and then contributes no values. The portal parses present files itself, rejects undeclared or duplicate keys, merges the values with measured environment, and passes explicit environment entries to Podman. It never passes the operator file through Podman's `--env-file` option.

`config` JSON shape — see [init-config-spec.md](init-config-spec.md) for the authoritative schema, field semantics, producer mapping, and persistence:

All keys use a unified `KeyConfig` shape: `mode` (self_generated | provisioned), `type` (es256k | es256 | rs256, matching on-chain `PublicIdentity.typeId`), and optional `private_key` (required when mode = provisioned).

`disk_setup` authorizes disk creation or explicit overwrite. It never carries secrets. `/init` rejects nonempty `disks` entries. Passphrase-enabled workloads require a provisioned owner key.

Use `GET /disks/{name}/unlock` for a fresh challenge and owner-signed `POST /disks/{name}/unlock` to submit one passphrase. Both use the persistent HTTPS listener on port 2024. `/status.disks` reports each disk separately. See [Disk unlock](disk-unlock-spec.md) for the signing format, states, and reboot workflow.

- `owner_operations.op_expiry_seconds`: seconds. Default validity window for
  owner-key-signed contract operations. It is not a session lifetime; that is
  controlled by workload `sessionTtl` policy.

- `owner_key`: signs `registerSession` authorization messages on-chain. The owner fingerprint is also bound into the TPM quote nonce. Always provisioned by the operator.
- `gas_wallet`: the relayer key that signs the on-chain transaction and pays gas.
  It is required and non-null. It can be self-generated or provisioned.
  atakit-portal holds it and owns every registration transaction.
- `chain.tee_backend`: `auto` uses ZK for SNP and Solidity/DCAP for TDX. `zk` selects a negotiated prover program for either TEE; `solidity` is rejected for SNP.
- `prover`: selects an installed out-of-process prover daemon and execution mode. The portal verifies its descriptor and capabilities before accepting a proof. Prover SDKs and guest programs are not linked into the portal.
- `prover_credential`: is retained by the portal supervisor. The daemon receives only delegated digest-signing access over a private Unix socket. A network prover requires this separate credential; `gas_wallet` is never a fallback.
- `pcr_policy`: is a strict `ResolvedPcrPolicy` value used only for Quote
  collection when `SessionRegistry.getPcrPolicy` is unavailable. It does not
  replace trusted verification policy. See
  [init-config-spec.md](init-config-spec.md#pcr-policy).

The portal and operator configuration accept only the current schema. They
reject the removed `sp1_payer`, `chain.proving_strategy`, and
`chain.transaction_submitter` fields. See
[atakit-prover-protocol-spec.md](atakit-prover-protocol-spec.md) and
[atakit-prover-artifact-spec.md](atakit-prover-artifact-spec.md).

**Fields explicitly absent vs legacy cvm-agent:**
- `relay_private_key` - renamed to `gas_wallet` with the unified key config shape.
- `owner_private_key` - renamed to `owner_key` with the unified key config shape.
- `cvm_agent_policy.json` contents - replaced by `manifest.json` inside the archive.

**Response**:
- `201 Created` with JSON body: `{transfer_id, atawl_transfer_duration_ms, state, base_image_id, base_image_ref, workload_id, workload_ref, gas_wallet_address, owner_key_fingerprint, tls_cert_fingerprint, started_at}`. `atawl_transfer_duration_ms` is the exact interval excluded from the client's one non-transfer initialization deadline.
- `409 Conflict` if already initialized.
- `401 Unauthorized` with `init_unauthorized` for missing or invalid initialization authorization. This does not consume the one-shot gate.
- ATAWL transfer and remote delivery add `invalid_atawl_source`, `atawl_size_mismatch`,
  `atawl_hash_mismatch`, and `atawl_workload_id_mismatch` validation errors,
  `atawl_download_failed` with HTTP 502, and `atawl_transfer_timeout` with
  HTTP 504. The timeout code applies to both binary upload receipt and remote
  download for compatibility.
- `initialization_timeout` with HTTP 504 when the non-transfer initialization
  budget expires. The portal enters terminal `Failed`.
- `500 Internal Server Error` when selected prover startup fails, including an
  unsafe/missing artifact, spawn/readiness failure, protocol mismatch, signer
  mismatch, or missing/duplicate required attestation program. The portal
  cleans up the partial daemon, persists terminal `Failed`, and does not start
  workload containers.

After a successful `/init`, the firewall rule that allows `:1024` is removed. Subsequent connections to `:1024` time out at the network layer.

### `GET /status` (`:2024`, always)

Returns portal lifecycle state and public identity. No authentication.

`startup_checks` reports Portal's local checks before workload disks and containers
start. It is public diagnostic data, not attestation or permission to release
secrets. Consumers must independently verify fresh evidence and use a trusted
source of expected measurements before provisioning secrets. See the
[provisioning security notice](secret-provisioning-security-notice.md).

| Field | Meaning |
|---|---|
| `scope` | Always `portal_local_startup`. |
| `status` | `not_run`, `running`, `passed`, `failed`, or `skipped`. |
| `source` | `not_selected`, `publisher_signed_registry`, or `initialization_policy`. |
| `stage` | Last stage reached: identifiers, policy read, signature checks, policy requirements, measurements, PCR comparison, or complete. Machine-readable values use underscores, such as `workload_signature` and `pcr_comparison`. |
| `workload_id`, `base_image_id`, `platform_profile_id`, `variant_id` | Selected IDs, or null if selection has not completed. |
| `workload_publisher`, `base_image_publisher` | Publisher fingerprints, populated only after the corresponding signature and identity checks pass. Publishers may differ. |
| `workload_policy_digest`, `base_image_policy_digest` | SHA-256 of the signed policy payload, or null before verification. |
| `workload_signature`, `base_image_signature` | `not_checked`, `passed`, or `failed`. Initialization policies have no publisher signature check. |
| `pcr_checks` | Completed comparisons, in evaluation order, through the first failure. Each entry contains `block` (`invariant`, `variant`, or `workload`), `bank`, `index`, `status`, `comparison`, `expected`, `actual`, `rule_digest`, and `detail`. |
| `detail` | Failure or skip reason, otherwise null. Missing measurements and malformed policies can fail before a comparison entry exists. |
| `hardware_verification` | Always `not_performed`; these startup checks do not verify full hardware evidence. |
| `secret_provisioning` | Always `requires_independent_verification`, including when status is `passed`. |

PCR values and digests use `0x` hex. Static and extend-from-zero rules expose the
expected PCR value. Dynamic rules expose their comparison type and SHA-256
`rule_digest`, with `expected: null`; they do not have one fixed expected value.
The report does not copy complete event logs or policy rules into `/status`.
A rule failure records the observed value and evaluator error.

The report lives in memory, resets on a new initialization attempt and at boot,
and remains available after startup fails. A `passed` report describes only
that startup attempt; it does not continuously monitor PCRs. With registration
off and no initialization policy, startup records `skipped`, never `passed`.
Clients must accept the field being absent on older Portal versions.

### Storage observations

`storage` reports filesystem counters read by the supervisor. It is informational;
it does not delete files, resize disks, change quotas, or stop workloads.

| Field | Meaning |
|---|---|
| `sampled_at_ms` | Guest wall-clock collection time, in milliseconds since Unix epoch; null while first collection is pending. Not a trusted timestamp. |
| `stale`, `refreshing` | Whether the cached report needs refresh and whether a refresh is in progress. |
| `low_space_percent` | Warning threshold: available space below 10% of filesystem capacity. |
| `truncated` | More than 64 entries were available; only the first 64 are included. |
| `error` | Fixed collection error code, or null. No raw operating-system error text. |
| `entries` | Portal writable storage, container image storage, declared workload disks, and mounted baby-root filesystems. |

Each entry contains `kind`, `name`, `state` (`available` or `unavailable`),
`filesystem_id`, `capacity_bytes`, `used_bytes`, `available_bytes`, `low_space`,
`quota`, and `error`. A workload disk must be mounted at its exact expected path;
locked or unmounted disks have null counters, never zero usage. An unavailable
image-store mount is treated the same way. Equal `filesystem_id` values mean
shared filesystem counters within the current boot. Do not add capacities:
separate loop-backed filesystems also consume space in their backing filesystem.
Used bytes exclude free blocks; available bytes also exclude reserved blocks,
so used plus available may be smaller than capacity.

For mounted baby roots, `quota` reports kernel project accounting as
`used_bytes`, `limit_bytes`, `used_inodes`, and `limit_inodes`. Null means quota
accounting is unavailable. Closed baby-root filesystems are not enumerated.
Quota usage is distinct from filesystem usage and must not be added to it.

The supervisor and worker cache readings for ten seconds each. `/status` waits
at most 200 ms for a new storage reading, then returns cached or pending data.
A pending supervisor call continues to consume its reply safely. Collection
uses bounded mount-table and manifest reads and filesystem/quota syscalls;
it never walks workload files. Older Portal versions omit `storage`.

Collection codes: `collection_pending`, `storage_read_failed`,
`mount_table_unavailable`, `disk_inventory_unavailable`. Entry codes:
`not_mounted_or_locked`, `filesystem_read_failed`, `quota_unavailable`.

`atakit` must read `init_schema_version` and `init_timeout_mode` immediately
before the one-shot `POST /init`. It must stop before `POST /init` if either
field is absent or does not equal the protocol it produces.

`chain.status` is one of `off`, `pending`, `preparing`, `ready`, `submitting`,
`submitted`, `verified`, or `failed`. `preparing` means an authorized
lifecycle request is building its successor candidate. The predecessor remains
the committed active session until the candidate is ready and confirmed.
Committing a local-bound successor updates `chain.session_id` but preserves
`chain.status` and `chain.detail`: `off` stays `off`, and an optional-
registration fallback stays `failed` with its recorded reason.

Served by the worker from local snapshots. The lifecycle cache is seeded from a
`GetState` RPC at startup and updated on each state transition. The platform
snapshot comes from the supervisor's authoritative `PlatformIdentity` and is
refreshed after `/init`; the worker never resolves cloud identity itself.
`platform.cloud_type` is the sole current cloud value used by all consumers.
`platform.attestation_mode` is derived from the authoritative `tee_type` and
does not create another mutable state source. `platform.build_profile` is the
compile-time artifact profile. Production packaging MUST run
`atakit-portal --build-profile`, require the exact output `production`, and
reject `tee_emulation` before installing the binary into an image.
`cloud_provenance.detection` is an observation record, not parallel current
state. It retains DMI text (with only sysfs line terminators removed), bounded
CSP-specific metadata responses, each detector's inference, the exact accepted
operator declaration, and the source that authorized `cloud_type`. Every probe
field is present. An unattempted probe uses `attempted=false`, empty headers,
and `null` status/body/error. Transport and validation failures use
`matched=false` and populate `error`. AWS IMDSv2 tokens are never serialized.
TEE detection and machine type are also captured by the supervisor and remain
immutable for the lifetime of the CVM.

`chain.tee_backend` echoes the configured policy. `prover` is present only
when a ZK prover configuration was resolved and exposes no endpoint, options,
credential identity, or private key material.

### `GET /platform-measurements` (`:2024`, always)

Returns TPM PCR values from both SHA-256 and SHA-384 banks plus a verifier-shaped event log. No authentication. **TPM-only**: TEE attestation evidence has its own endpoint at `GET /tee-evidence` (see below).

This is the verifier endpoint. Each event entry exposes only the fields a verifier needs to compute against — the canonical TCG event-type id and the per-bank digests committed into the PCR. Entries with event type `EV_NO_ACTION` (`0x00000003`) are excluded because they do not extend a PCR. IMA entries use event type id `0` and are retained because they do extend PCR10. The parsed forensic view is exposed via `GET /event-log`; consumers that need the exact original kernel files use `GET /event-log/raw`.

Response shape:

```json
{
  "pcrs": [
    { "index": 0,  "sha256": "0x<64-hex-digits>", "sha384": "0x<96-hex-digits>" },
    { "index": 1,  "sha256": "0x<64-hex-digits>", "sha384": "0x<96-hex-digits>" },
    ...
    { "index": 23, "sha256": "0x<64-hex-digits>", "sha384": "0x<96-hex-digits>" }
  ],
  "event_log": [
    { "pcr_index": 0, "event_type_id": 8, "sha256_digest": "0x<64-hex-digits>", "sha384_digest": "0x<96-hex-digits>" },
    ...
  ]
}
```

- `pcrs` always has all 24 entries (indexes 0-23) with both bank values. Pre-init, PCR23 is the zero hash in both banks; post-init it is `SHA-256(zeros_32 || SHA-256(manifest.json))` in the SHA-256 bank and `SHA-384(zeros_48 || SHA-384(manifest.json))` in the SHA-384 bank — the same input bytes hashed under each bank's algorithm. PCR15 is similarly extended in both banks.
- `event_type_id` is the canonical UINT32 TCG event-type identifier (e.g. `8` for `EV_S_CRTM_VERSION`, `0x80000003` for `EV_EFI_BOOT_SERVICES_APPLICATION`). Verifiers should match on this id rather than on any rendered string.
- `sha256_digest` and `sha384_digest` are the per-bank digests committed into the PCR by this event. UEFI/firmware events provide both; supervisor-emitted events provide both; IMA runtime events provide `sha256_digest` only (kernel default; `sha384_digest` is omitted or zero per the IMA template). These fields support per-bank measurement-pack generation, diagnostics, and dynamic-policy witnesses. The decided AWS verifier does not derive SHA-384 policy from SHA-256 event digests and does not prove cross-bank identity from one caller-supplied event log; see the registry reference.

Served by the worker. The worker queries the supervisor via `GetPlatformMeasurements` RPC for TPM PCR/event-log data.

Same response shape regardless of CVM state. PCR values differ by state. Event entries grow monotonically within a single boot: UEFI events are written once by firmware before kernel handoff, IMA grows as the kernel measures files at runtime, and supervisor-emitted events are appended at the corresponding state transitions. A reboot resets the log — UEFI is re-written by firmware, IMA starts empty, and the supervisor re-emits its own events as init re-runs.

### `GET /event-log` (`:2024`, always)

Returns the parsed aggregate event log with every retained per-entry field — mnemonic, canonical id, per-bank digests, raw event payload bytes, and a best-effort human-readable description. Forensic / debug counterpart to `/platform-measurements`. This is not a byte-exact copy of the kernel log files; use `/event-log/raw` for that.

No authentication. Returns the same response shape regardless of CVM state.

Response shape:

```json
{
  "events": [
    {
      "pcr_index": 0,
      "event_type": "EV_S_CRTM_VERSION",
      "event_type_id": 8,
      "sha256_digest": "0x<64-hex-digits>",
      "sha384_digest": "0x<96-hex-digits>",
      "event_payload": "<base64url>",
      "description": "..."
    },
    ...
  ]
}
```

- `event_type` is a best-effort mnemonic rendered by the worker from a TCG type table. Verifiers must not depend on the string — match on `event_type_id` instead. The mnemonic is for human consumption.
- `event_type_id` is the canonical UINT32 TCG event-type identifier.
- `sha256_digest` and `sha384_digest` are the per-bank digests committed into the PCR by this event. IMA runtime events typically supply only `sha256_digest` (kernel default template); UEFI/firmware events and supervisor-emitted events supply both.
- `event_payload` is the raw `Event` field bytes for UEFI, the template-data bytes for IMA, or the supervisor-defined payload for portal events, base64url-encoded.
- `description` is a best-effort human-readable rendering of `event_payload` per the event type's known structure (UCS-2 for `EV_S_CRTM_VERSION`, UEFI device path for `EV_EFI_BOOT_SERVICES_APPLICATION`, etc.). Verifiers must not depend on it.

`events[]` aggregates UEFI/TCG firmware events, IMA runtime events, and supervisor-emitted events (e.g. PCR23 manifest extend at `/init`). Same monotonic-within-boot semantics as `/platform-measurements.event_log`.

Served by the worker. Same `GetPlatformMeasurements` RPC source as `/platform-measurements`; the worker projects the supervisor's full event records to this endpoint's response shape.

### `GET /event-log/raw` (`:2024`, always)

Returns the exact, unmodified bytes read from the kernel's firmware and IMA TPM event-log files. This is the lossless forensic endpoint: the firmware bytes include the initial Spec ID `EV_NO_ACTION` record and retain original record framing. It does not include supervisor-emitted parsed events, which are not part of either kernel file and remain available through `/event-log`.

No authentication. The response is marked `Cache-Control: no-store`. Binary values use unpadded base64url. Both fields are always present; a kernel log that is not exposed is represented by `null`, while a present empty file is an empty base64url string.

```json
{
  "format": 1,
  "firmware_event_log": "<base64url>",
  "ima_event_log": null
}
```

- `firmware_event_log` is the exact content of `/sys/kernel/security/tpm0/binary_bios_measurements`.
- `ima_event_log` is the exact content of `/sys/kernel/security/ima/binary_runtime_measurements`.

Served by the worker through bounded `GetRawTpmEventLogChunk` supervisor RPCs.
The combined raw firmware and IMA bytes MUST NOT exceed 33,554,432 bytes. A
larger or continuously growing log returns `413 Payload Too Large`. The worker
assembles only one raw event-log response at a time; another concurrent request
returns `429 Too Many Requests` with `Retry-After: 1`. These bounds limit both
worker memory and supervisor IPC work. The unprivileged worker does not
directly read securityfs.

### `GET /tee-evidence` (`:2024`, always)

Returns TEE-side attestation evidence: the signed report/quote, vendor cert material, and AK-binding material. No authentication. Disjoint from `/platform-measurements`: that one is TPM-only PCRs/event-log, this one is TEE evidence and surrounding material a verifier toolchain consumes when assembling the on-chain `AttestationEvidence` bundle (see [cvm-registry/types-constants-libraries.md](cvm-registry/types-constants-libraries.md)).

Response shape:

```json
{
  "cloud":     "gcp" | "aws" | "azure" | "qemu" | "unknown",
  "cloud_provenance": {
    "source": "dmi" | "metadata" | "user_provided" | "unresolved",
    "detection": {
      "dmi": {
        "sys_vendor": "Google" | null,
        "product_name": "Google Compute Engine" | null,
        "bios_vendor": "Google" | null,
        "detected_cloud": "gcp" | "unknown"
      },
      "metadata": {
        "gcp": {"attempted": true, "matched": true, "http_status": 200, "response_headers": {"metadata-flavor": "Google"}, "response_body": "instance/\nproject/\n", "error": null},
        "azure": {"attempted": false, "matched": false, "http_status": null, "response_headers": {}, "response_body": null, "error": null},
        "aws": {"attempted": false, "matched": false, "http_status": null, "response_headers": {}, "response_body": null, "error": null},
        "detected_cloud": "gcp",
        "conflict": false
      }
    },
    "user_provided": "gcp" | null
  },
  "tee_type":  "sev-snp" | "tdx" | "sev-es" | "sev" | "emulation" | "none",
  "report":    "<base64url>",
  "auxiliary": { "kind": "amd-snp-certs", "vcek"?: "<b64>", "vlek"?: "<b64>", "ask"?: "<b64>", "ark"?: "<b64>" } | null,
  "akbind":    { "kind": "cert-chain", "certs": ["<b64>", ...] }
            |  { "kind": "azure-jwk",  "data":  "<b64>" }
            |  null
}
```

Per backend:

| Cloud × TEE | `report` source | `auxiliary` | `akbind` |
|---|---|---|---|
| GCP/SEV-SNP | configfs-tsm `outblob` (1184 B SNP_REPORT) | parsed `auxblob` (VCEK + ASK + ARK) | `cert-chain`: ECC AK leaf from vTPM NV `0x01c10002`, parents fetched via AIA |
| GCP/TDX | exact TDQUOTE extracted from configfs-tsm `outblob`; provider-owned trailing zeros are removed | `null` | `cert-chain`: same as above |
| AWS/SEV-SNP | configfs-tsm `outblob` (1184 B SNP_REPORT) | parsed `auxblob` (VLEK only; ASK/ARK absent) | `null` (AWS vTPM has no AK cert) |
| Azure/SEV-SNP | inner SNP_REPORT from HCL (NV `0x01400001`) | `null` | `azure-jwk`: HCL `var_data` JSON |
| Azure/TDX | TDQUOTE (HCL TD_REPORT post-IMDS-conversion via `/acc/tdquote`) | `null` | `azure-jwk`: HCL `var_data` JSON |
| Any × Emulation | canned blob | `null` | `null` |
| Anything else (incl. `tee_type=none`) | empty string | `null` | `null` |

Validation done on the worker before returning:
- `report` is the raw signed-report bytes; verifier validates the signature off-chain (or via the on-chain `TeeVerifier`).
- An Intel TDX `report` ends immediately after its declared signature data.
  The provider adapter removes zero padding from a fixed-size provider buffer;
  every later consumer rejects all trailing bytes.
- For `akbind.cert-chain`, the worker structurally validates the chain (each cert parses, parent's Subject DN matches child's Issuer DN, bounded depth, byte cap, no AIA cycle). It does **not** verify signatures on the chain — that's the on-chain `tpmAttestation.verifyCertChain` job.
- Auxblob is parsed into named cert fields by AMD GUID; unknown GUIDs are dropped.

Errors:
- `503 Service Unavailable` if the supervisor's evidence fetch fails (configfs broken, IMDS unreachable on Azure TDX, etc.). Body: `{ "error": "<detail>" }`.
- `200 OK` with `tee_type: "none"` and empty `report` when running on hardware without a TEE (matches the `TeeType::None` design choice — supervisor still serves, evidence is just absent).

Served by the worker. Calls the supervisor's `GetTeeAttestation` RPC for raw evidence + GCP AK leaf, then walks the AIA chain (worker-local HTTPS to `pki.goog`) and assembles the response. AIA fetches are cached in-process for the worker's lifetime.

### `GET /tls-attestation` (`:2024`, always)

Returns a nonce-bound TLS bootstrap attestation bundle for the portal's
self-signed HTTPS certificate. This endpoint is available before `/init` and is
the intended first-contact trust path for clients that would otherwise need to
disable certificate validation.

Authoritative protocol details, response schema, CSP-specific verification
rules, measurement policy, failure reports, and manual override behavior are
defined in [tls-attestation-spec.md](tls-attestation-spec.md).

**Request:**

| Parameter | Type | Required | Description |
|---|---|---|---|
| `nonce` | base64url 32-byte value | yes | Client-generated freshness challenge. Padding is rejected. |

The TPM quote challenge is:

```text
qualifying_data = H(ATAKIT_TLS_BOOTSTRAP_V1, nonce, tls_cert_sha256)
```

The verifier MUST check that the returned TLS certificate hash matches the live
peer certificate from the bootstrap connection, that the TPM quote signs the
expected `qualifying_data`, and that the quote-signing AK is bound to the
attested CVM.

**Errors:**

- `400 Bad Request` - missing, malformed, padded, or wrong-length `nonce`.
- `503 Service Unavailable` - TPM, TEE evidence, or CSP collateral collection
  failure.

### Session and lifecycle endpoints (`:2024`, post-init only)

The current session surface is:

- `GET /session`
- `GET /session/evidence-bundle?challenge=...`
- `POST /session/new`
- `POST /session/rotate-key`
- `POST /session/renew`
- `POST /session/recover`
- `POST /challenge/authorize`
- `GET /session/status`
- `GET /requests/{request_hash}`

The complete schemas, hashes, challenge authorization, retention rules, and
local-versus-chain binding semantics are normative in
[session-attestation-spec.md](session-attestation-spec.md). The portal prepares
the challenge-bound calldata, signs it, broadcasts it, retries, checks receipts,
and confirms `isSessionActive` through `chain.rpc_url`. During a
lifecycle operation the committed predecessor remains active while one
successor candidate is pending. The request completes only after the successor
is active on chain and committed locally. All projection fields are always
present and use `null` when a value does not apply.

Before the first committed session, `GET /session` and
`GET /session/evidence-bundle` return `503 Service Unavailable` with
`Retry-After: 1` and the `session_not_ready` response defined in the session
attestation specification.

For an unknown portal-managed broadcast result, the portal retries only the
same signed transaction bytes with bounded backoff. It observes both the
locally calculated transaction hash and `isSessionActive` until
`op_expires_at`. It sends nothing after expiry and performs one final
`isSessionActive` check before applying the same terminal policy.

For every initial-registration and lifecycle submission attempt, the portal
checks `op_expires_at` before fee estimation, after fee estimation and before
`SignWithGasWallet`, and again immediately before
`eth_sendRawTransaction`. Expiry at any check is terminal and no later step in
that attempt runs. A retry whose backoff crosses the deadline stops before
starting retry work. The comparison matches the registry contract:
`now > op_expires_at` is expired, while equality is still valid.

## Consumer contracts

### `atakit-imgbuild`

- Hits `:2024/platform-measurements` on a test CVM in AwaitingInit (via `atakit cloud deploy --image-only`). Parses the full PCR dump and the verifier-shaped event log, deriving the golden profile per cloud. Match events on `event_type_id` (canonical TCG id), not on any rendered string.
- For human-readable golden registration metadata or to inspect raw `event_payload` bytes, hits `:2024/event-log` instead.
- May hit `:2024/tee-evidence` to capture per-cloud reference quote/report bytes.

- `post_init(ip, archive, config, unmeasured, timeout, progress)`: sends

## TLS

Self-signed ECDSA P-256 certificate, generated by the supervisor at first boot. Stored at `/atakit-portal/tls/cert.pem` + `key.pem`. The supervisor loads the cert and key, then passes them to the worker at fork time (in-memory). The worker uses them for both `:1024` and `:2024` listeners. Never rotated within a CVM's lifetime.

Clients SHOULD establish first-contact trust through
`GET /tls-attestation?nonce=...`, then pin the attested certificate for later
portal calls. The `/init` response returns the certificate fingerprint for
diagnostics.

## CPU controls (v0.3.6 and later)

The `cpu_idle` field of `GET /status` reports the CPU idle startup snapshot.
The `cpu_frequency` field of `GET /status` reports the CPU frequency policy startup snapshot,
including requested and applied governors and available governors per policy. Each
`containers.services` entry includes the configured `cpuset`, or null.
`POST /baby-container/create` accepts optional `cpuset` to select a subset of
its signed slot allowance. The selection persists across stop/start and
reboot. See [CPU controls](workload-cpu-controls.md) for exact behavior.

## Runtime disk configuration

Schema 4 adds `runtime_disks` to `/init`. The existing owner-authenticated
`POST /runtime-config` accepts optional CPU `selection`, disk `runtime_disks`, and `thp`
scopes. Omitted scopes preserve pending and active choices. Disk choices apply
before unlock on the next kernel boot. `GET /status` reports pending choices at
`runtime.pending.disks` and verified mapping flags at `runtime.observed.disks`. The exact request, signature,
limits and boot behavior are specified in
[cloud disk configuration](cloud-disk-configuration.md#portal-protocol-and-enforcement).

Runtime CPU, disk and THP status share the `runtime` object. See
[runtime configuration](runtime-configuration.md) for the fixed THP options,
persistence, and boot activation rules.
